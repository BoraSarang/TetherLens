## 2. 핵심 발견 — 이 프로젝트의 근본 제약

**`nettop` 은 프로세스별 네트워크 트래픽의 유일한 소스이고, 이 머신에서
어떤 설정으로도 ~135% CPU 를 쓴다.**

| 설정 | CPU |
|---|---|
| `-l 3 -s 1` | 136.8% |
| `-l 31 -s 1` | 136.9% |
| `-l 2 -s 30` | 133.7% |

### 이것이 만들어내는 트레이드오프

| 요구 | 필요 소스 | CPU | 상태 |
|---|---|---|---|
| 총 사용량 · 할당량 (2GB 추적) | 인터페이스 카운터 (무료) | 0% | ✅ **정상 작동** |
| 실시간 총 속도 (메뉴바/차트) | 인터페이스 카운터 (무료) | 0% | ✅ **정상 작동** |
| **"지금 누가 쓰지?"** | nettop | 135% | 클릭 시 3초 측정 |
| **"누가 제일 많이 썼냐" (통계)** | nettop | 135% | ❌ **미해결** |

**이 두 요구(실시간 + 통계)를 동시에, 저비용으로 만족시키는 방법을 찾지 못했다.**
libproc 로 프로세스별 네트워크 바이트를 얻는 공개 API 는 없다. `nettop` 이 private 를 쓴다고 추정된다.

## 3. 실측으로 확정된 버그 두 건

### ① `nettop` 첫 블록이 "0" 이 아니라 누적 카운터 스냅샷

같은 5초 구간을 인터페이스 카운터와 대조했다.

| | 값 |
|---|---|
| 인터페이스 실제 카운터 델타 | 64,671 B |
| nettop **block 1** 합계 | 16,050,290 B (실제의 248배) |
| nettop **blocks 2~6** 합계 | 17,834 B |

예전 주석의 "첫 블록은 기준점(모두 0)" 이 틀렸고, 그 전제 아래 **전 블록을 합산**했다.
덕분에 2 KB/s 인 화면에서 프로세스 하나가 22 MB/s 로 표시됐다.
`TrafficMonitor.parse` 가 첫 블록을 제외하도록 수정했고, `samples` 는 `interval + 1` 로 보정했다
(첫 블록이 기준점이므로 1초를 잃는다).

### ② 목록 필터가 "한 번이라도 쓴 적 있음"으로 걸렀다

`bytesIn > 0 || bytesOut > 0 || totalBytes* > 0` 중 마지막 항 덕분에
지금 트래픽이 0 인 프로세스가 목록에 계속 남아 있었다. **현재 구간만** 남기도록 수정.

## 4. ⚠️ 남은 문제 (아카이브 사유)

### ① `app_traffic_log` 테이블이 오염돼 있다 (85 TB)

첫 블록 버그로 `adb` 프로세스 하나가 매 5분마다 676GB씩 기록됐다.

```
app_traffic_log: adb 합계 = 85,847,244,330,736 B (85 TB), 4,209행
```

**코드는 고쳤으니 더 이상 쌓이지 않는다.** 하지만 과거 데이터는 남아있어
앱별 트래픽 리포트에 섞인다. **정리하려면 삭제가 필요하며 되돌릴 수 없다 —
사용자 승인을 받지 않아 수행하지 않았다.**

### ② 프로세스별 통계가 끊겼다

`f4814f4` 이후 상시 nettop 측정을 껐다(배터리). 프로세스별 **과거 통계**는 이제 쌓이지 않는다.
사용자가 켤 수는 있다: 설정 > 대시보드 > 프로세스 트래픽 > 항상 측정.
단 켜면 CPU 비용을 치른다.
